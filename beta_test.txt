# Registro de verificaciones beta — IMA

## TASK-047 / AUD-NG-090 — comunicación entre cuentas y deployments Apps Script

- Estado: Pendiente beta.
- Motivo: requiere dos cuentas Google institucionales autorizadas y deployments reales independientes. No se dispone en esta iteración de acceso aprobado a esas cuentas/proyectos; no se publican endpoints ni se solicitan secretos.
- Alcance por verificar:
  1. Registrar desde la consola de Desarrollador un servicio alojado bajo cada cuenta institucional, con su proyecto Apps Script, URL, Spreadsheet, carpeta Drive, dominio, rol/puesto y modalidad.
  2. Confirmar que cada cuenta puede desplegar su servicio y que el endpoint conserva la privacidad institucional configurada, sin hacerlo público.
  3. Iniciar sesión una sola vez en el portal y comprobar que el enrutador selecciona el servicio individual correcto según rol/identidad; verificar el servicio compartido Padres/Estudiantes donde aplique.
  4. Ejecutar acciones permitidas y denegadas para verificar permisos por acción y que el servicio suspendido/retirado no recibe nuevas solicitudes.
  5. Cambiar responsable, endpoint y recursos; comprobar historial y autorización efectiva actualizados.
  6. Verificar con Google Workspace que las restricciones de dominio son efectivas y que el acceso a Sheets/Drive corresponde a la cuenta propietaria.
  7. Confirmar que los permisos de almacenamiento no se confunden con privilegios institucionales de la plataforma.
- Evidencia requerida: resultados de cada escenario, identificadores de despliegue redactados, estado de acceso y fecha de prueba; nunca copiar tokens, secretos ni URLs sensibles al repositorio.
- No bloqueante para implementación local: los contratos, fixtures y pruebas locales del registro/enrutamiento ya pasan. La prueba beta no se declara aprobada ni ejecutada.

## TASK-004 / F16-TASK01 — integración desplegada del catálogo de responsabilidades de RR. HH.

- Estado: Pendiente beta.
- Motivo: requiere el servicio USER Apps Script y una cuenta institucional de prueba con permisos de RR. HH.; las pruebas de contrato no validan persistencia real en Sheets ni la interacción del navegador con el deployment.
- Precondiciones: deployment USER institucional disponible; usuario de prueba autorizado; empleados y departamentos sintéticos; Spreadsheet de prueba aislada. No usar datos productivos.
- Pasos:
  1. Abrir el panel de RR. HH. y consultar catálogo, empleados, departamentos y asignaciones.
  2. Crear y editar una responsabilidad; confirmar persistencia, unicidad de nombre/código y estado.
  3. Asignar dos responsabilidades distintas a un empleado activo y una responsabilidad a dos empleados; comprobar fechas y ámbito.
  4. Registrar una suplencia dentro de la vigencia del titular y rechazar una suplencia con período solapado.
  5. Revocar una asignación y comprobar que la fila y el historial de auditoría conservan actor y motivo.
  6. Confirmar que la responsabilidad no modifica los permisos RBAC del rol de acceso ni permite acciones administrativas no concedidas.
  7. Consultar historial tras desactivar una responsabilidad o revocar una membresía y comprobar que no se pierde la trazabilidad.
  8. Comprobar que las fechas de fin de mes y años bisiestos se conservan al persistir y volver a consultar.
- Resultado esperado: UI y servicio USER mantienen el catálogo y asignaciones coherentes; errores se muestran sin duplicar escrituras; historial íntegro; RBAC permanece separado.
- Evidencia requerida: fecha, versión del deployment, resultados por escenario y registros de prueba redactados. No incluir tokens, datos personales reales ni URLs sensibles.
- No bloqueante para implementación local: esta validación depende de Apps Script/Sheets desplegados y se ejecutará en beta.

## TASK-505 / AUD-NG-225 — dashboard dinámico y navegación por rol

- Estado: Pendiente beta.
- Motivo: los contratos actuales verifican la lectura del rol desde la columna real de Usuarios y que cada tarjeta tenga una ruta a un dashboard existente, pero no sustituyen la validación del USER Apps Script desplegado ni la navegación real en navegador.
- Precondiciones: deployment USER institucional disponible; Spreadsheet de prueba aislada; dos cuentas sintéticas activas con roles Docente y Secretaría; dashboards destino desplegados; permisos RBAC de prueba configurados.
- Pasos:
  1. Iniciar sesión como Docente y abrir el dashboard dinámico; comprobar que rolPrincipal coincide con Usuarios.Rol y que las tarjetas corresponden al catálogo de ese rol.
  2. Repetir con Secretaría y confirmar que no se reutilizan módulos del usuario anterior.
  3. Abrir cada tarjeta y comprobar que navega al dashboard existente correcto; volver atrás y repetir tras cambiar de usuario/rol.
  4. Intentar una acción backend no autorizada para cada rol mediante llamada directa; comprobar denegación RBAC aunque el módulo o enlace se manipule desde el cliente.
  5. Verificar que una cuenta inexistente/inactiva no recibe datos de otra cuenta ni una navegación privilegiada.
- Resultado esperado: el rol y las tarjetas reflejan el usuario autenticado; cada ruta existe y navega al destino previsto; la navegación no concede permisos backend adicionales.
- Evidencia requerida: fecha, versión del deployment, rol sintético, rutas probadas, resultado de acciones permitidas/denegadas y capturas redactadas. No incluir tokens, datos personales reales ni URLs sensibles.
- No bloqueante para implementación local: contratos Node.js y revisión de rutas pasan; la validación requiere despliegue institucional y navegador.
